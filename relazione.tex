\begin{abstract}
Il presente documento descrive la progettazione e l'implementazione della libreria \texttt{FSStatLib}, sviluppata in Java 21+. L'obiettivo del 
progetto è analizzare un albero di directory del file system, calcolando il numero totale di file e la loro distribuzione in fasce di dimensione. 
L'elaborazione è stata parallelizzata utilizzando tre metodi e tecnologie differenti: i Virtual Threads, 
programmazione asincrona basata su event loop, e la programmazione reattiva con RX.
\end{abstract}

\section{Introduzione e Requisiti}

\subsection*{Obiettivo}

L'obiettivo è la realizzazione della libreria \texttt{FSStatLib}, che espone un metodo asincrono \texttt{getFSReport} per l'analisi statistica delle dimensioni dei file contenuti in un albero di directory del file system. Dato un percorso radice \texttt{D}, il metodo calcola e restituisce in modo asincrono un report \texttt{R} contenente:

\begin{itemize}
    \item il \textbf{numero totale di file} presenti in \texttt{D}, incluse ricorsivamente tutte le sottodirectory;
    \item la \textbf{distribuzione delle dimensioni} dei file: dato un valore massimo di dimensione \texttt{MaxFS} e un numero di bande \texttt{NB}, il range \texttt{[0, MaxFS]} viene suddiviso in \texttt{NB} intervalli di ampiezza uniforme; per ciascun intervallo viene contato il numero di file la cui dimensione vi rientra. Viene inoltre conteggiata separatamente la quantità di file con dimensione superiore a \texttt{MaxFS}. Il report include quindi complessivamente \texttt{NB + 1} contatori.
\end{itemize}

I parametri \texttt{D}, \texttt{MaxFS} e \texttt{NB} sono forniti dal chiamante come argomenti del metodo.

\subsection*{Versioni implementate}

Il progetto è stato declinato in \textbf{tre versioni indipendenti}, ciascuna aderente a una specifica disciplina di programmazione concorrente discussa durante il corso:

\begin{enumerate}
    \item \textbf{Virtual Threads} (Java): paradigma \textit{thread-per-task} con Virtual Thread leggeri gestiti dalla JVM.
    \item \textbf{Programmazione asincrona basata su Event Loop}: composizione di operazioni non bloccanti.
    \item \textbf{Programmazione reattiva con RX}: modellazione del file system traversal come stream di eventi, elaborato tramite operatori funzionali (RxJava).
\end{enumerate}

Un vincolo di progetto esplicito impone che le tre versioni siano sviluppate in modo \textbf{indipendente}, senza generalizzare o riutilizzare codice tra di esse qualora ciò compromettesse la purezza della disciplina di programmazione propria di ciascun approccio.

\subsection*{Requisito opzionale}

Il progetto prevede un requisito opzionale, che estende la libreria con funzionalità interattive:

\begin{itemize}
    \item possibilità di \textbf{interrompere} la generazione del report in qualsiasi momento;
    \item \textbf{aggiornamenti dinamici} delle statistiche durante la computazione, visualizzabili in tempo reale.
\end{itemize}

A supporto di queste funzionalità è prevista una \textbf{GUI minimale}, dotata di controlli per avviare e interrompere la scansione e di un'area di visualizzazione per il monitoraggio progressivo del report.
\section{Analisi del Problema e Scelte Concorrenti}
L'attraversamento ricorsivo di un file system e l'interrogazione delle proprietà dei file sono tipiche operazioni legate all'I/O. In questi scenari di I/O-bound, l'uso intensivo dei classici thread di piattaforma presenta gravi limiti di scalabilità. Per esplorare soluzioni diverse a questo problema di concorrenza, il progetto è stato declinato in tre paradigmi distinti.

\subsection{Approccio con i Virtual Threads}

I Virtual Threads, introdotti stabilmente in Java 21, sono thread \textit{user-mode} gestiti dalla JVM anziché dal sistema operativo. Rispetto ai \textit{platform thread}, il loro overhead di creazione e il consumo di memoria sono trascurabili, il che li rende adatti a un modello \textit{Thread-per-task}: è possibile istanziarne decine di migliaia senza incorrere in \texttt{OutOfMemoryError} né in degrado delle prestazioni.

Questa caratteristica si adatta in modo naturale all'attraversamento ricorsivo di un albero di directory: la struttura del file system è intrinsecamente ramificata e imprevedibile, e ogni nodo (directory) richiede operazioni di I/O bloccanti a latenza variabile (apertura dello stream, lettura degli attributi dei file con \texttt{Files.size()}). Assegnare un Virtual Thread a ciascun nodo permette di sfruttare appieno la concorrenza senza dover dimensionare a priori un pool.

\paragraph{Struttura dell'implementazione.}

Il punto di ingresso pubblico è il metodo \texttt{getFSReport()}, che restituisce una \texttt{CompletableFuture<FSReport>} per offrire un'interfaccia non bloccante al chiamante (la GUI). Internamente, la computazione reale viene incapsulata in una \texttt{CompletableFuture.supplyAsync()}. Prima di avviare la scansione viene istanziato un unico \texttt{FSReport} \textit{condiviso} tra tutti i Virtual Thread, e viene creato un \texttt{ExecutorService} dedicato tramite \texttt{Executors.newVirtualThreadPerTaskExecutor()}, racchiuso in un blocco \texttt{try-with-resources}:

\begin{lstlisting}[language=Java]
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Path rootPath = Paths.get(directoryPath);
    processDirectory(rootPath, executor, sharedReport, onUpdate, controller).get();
    return sharedReport.getSnapshot();
}
\end{lstlisting}

La chiusura automatica dell'executor al termine del blocco \texttt{try} ha una semantica cruciale:
\texttt{ExecutorService.close()}, (che viene invocato automaticamente nel blocco \texttt{try-with-resources}) invoca \texttt{shutdown()} seguito da \texttt{awaitTermination()},
garantendo che nessun task figlio venga abbandonato prima che il risultato finale sia disponibile.
 Questo meccanismo funge da \textit{barriera di sincronizzazione} implicita su tutto l'albero dei task.

\paragraph{Ricorsione concorrente su stato condiviso.}

Il metodo \texttt{processDirectory()} incarna il pattern \textit{divide et impera}: per ogni nodo dell'albero viene sottomesso all'executor un nuovo task (e quindi un nuovo Virtual Thread), a cui vengono passati per riferimento lo stesso \texttt{ExecutorService} e lo stesso \texttt{FSReport} \textit{condiviso} tra tutti i task, anziché un report locale al singolo thread. All'interno del task, si itera sul contenuto della directory tramite \texttt{Files.newDirectoryStream()}:

\begin{itemize}
    \item Per ogni \textbf{file regolare}: si invoca \texttt{Files.size()} (operazione I/O bloccante) e si registra il file direttamente sul \texttt{FSReport} condiviso tramite \texttt{addFile()}, un'operazione atomica protetta internamente da un lock.
    \item Per ogni \textbf{sottodirectory}: si sottomette ricorsivamente un nuovo task all'executor, raccogliendo il \texttt{Future<Void>} restituito in una lista di \textit{subTask}.
\end{itemize}

Terminata la scansione della directory corrente, il Virtual Thread chiama \texttt{task.get()} su ciascun subTask per attenderne il completamento; non essendo più necessaria alcuna fusione di risultati (il report è già aggiornato in modo condiviso da tutti i task), questa fase svolge esclusivamente il ruolo di \textit{join} strutturale, propagando verso l'alto sia il completamento sia — se richiesta — la cancellazione:

\begin{lstlisting}[language=Java]
for (Future<Void> task : subTasks) {
    if (controller.isCancelled()) {
        task.cancel(true);
    } else {
        task.get();
    }
}
\end{lstlisting}

La struttura risultante rimane un albero di Virtual Thread isomorfo all'albero delle directory: la fase di \textit{map} distribuisce il lavoro di scansione su Virtual Thread indipendenti, ma a differenza di un classico pattern Map-Reduce non esiste più una fase di \textit{reduce} esplicita, poiché ogni task scrive direttamente sull'unico stato condiviso.

\paragraph{Sincronizzazione dello stato condiviso: \texttt{ReentrantLock} e Thread Pinning.}

Poiché tutti i Virtual Thread accedono concorrentemente allo stesso \texttt{FSReport}, l'incremento del contatore e dell'array \texttt{distribution} in \texttt{addFile()} costituisce una sezione critica e richiede sincronizzazione esplicita. La scelta è ricaduta su un \texttt{java.util.concurrent.locks.ReentrantLock} piuttosto che su un blocco \texttt{synchronized}: quest'ultimo, se acquisito da un Virtual Thread che si blocca al suo interno (ad esempio in attesa di un altro lock), può causare il fenomeno del \textit{Thread Pinning}, per cui il Virtual Thread rimane ``fissato'' al proprio carrier thread invece di poter effettuare l'unmount, vanificando il vantaggio dei Virtual Thread in presenza di elevata contesa. Il \texttt{ReentrantLock}, gestito interamente a livello di libreria concorrente e non tramite bytecode di monitor, non soffre di questa limitazione e consente comunque l'unmount del Virtual Thread in attesa del lock.

\paragraph{Cancellazione cooperativa e aggiornamenti incrementali.}

A supporto del requisito opzionale di interruzione e monitoraggio in tempo reale, \texttt{getFSReport()} accetta due parametri aggiuntivi opzionali: un \texttt{Consumer<FSReport>} \texttt{onUpdate} e un oggetto \texttt{TaskController}, che espone un flag \texttt{volatile} interrogabile tramite \texttt{isCancelled()} e impostabile tramite \texttt{cancel()}. Ogni task verifica tale flag prima di iniziare la scansione di una directory e a ogni iterazione al suo interno, interrompendo tempestivamente l'esplorazione dei rami non ancora visitati senza dover implementare un vero e proprio meccanismo di interrupt sui thread. Ogni \texttt{NOTIFY\_EVERY\_N\_FILES} file processati viene inoltre notificata al chiamante una \textit{snapshot} immutabile e coerente del report parziale tramite \texttt{onUpdate.accept()}, permettendo l'aggiornamento in tempo reale dell'interfaccia utente senza esporre lo stato mutabile interno. La versione ``semplice'' del metodo, richiesta come requisito base, delega semplicemente a questa versione completa passando \texttt{onUpdate = null} e un \texttt{TaskController} locale non condiviso col chiamante.

Quando un Virtual Thread si blocca su un'operazione di I/O — ad esempio \texttt{Files.size()} — sull'acquisizione del \texttt{ReentrantLock}, oppure su \texttt{task.get()} in attesa di un risultato non ancora
disponibile — la JVM effettua automaticamente l'\textit{unmount} del Virtual Thread dal \textit{carrier thread} (il platform thread sottostante), che viene immediatamente liberato
 per eseguire un altro Virtual Thread pronto.
 Questo meccanismo permette al ridotto pool di carrier thread (tipicamente uguale al numero di core fisici) di servire migliaia di Virtual Thread concorrenti, eliminando il costo del
 context switch a livello di sistema operativo.


\subsection{Approccio Asincrono basato su Event Loop}

Il secondo paradigma adottato si basa sul modello \textit{Event Loop}, incarnato in questa implementazione dal runtime \textbf{Node.js} (scritto in TypeScript). In questo modello, un \textbf{singolo thread JavaScript} esegue il codice applicativo, delegando tutte le operazioni di I/O al layer sottostante \textit{libuv}, che le gestisce tramite un proprio thread pool interno al runtime. Al completamento di ciascuna operazione, la relativa callback viene accodata nell'event loop ed eseguita dal thread principale non appena questo è libero.

\paragraph{Adattamento al problema.}

L'attraversamento ricorsivo di un albero di directory è un workload \textit{I/O-bound} con un elevato grado di parallelismo naturale: i contenuti di directory diverse sono indipendenti tra loro e possono essere letti concorrentemente. Questo si adatta perfettamente al modello event loop, dove la concorrenza non è ottenuta tramite thread multipli ma tramite l'\textit{interleaving} di operazioni asincrone: il thread principale non attende mai il completamento di una lettura su disco, ma registra una \texttt{Promise} e prosegue a processare altri eventi già completati.

\paragraph{Concorrenza tramite \texttt{Promise.all}.}

Il cuore della concorrenza risiede nel metodo \texttt{traverseDirectory} di \texttt{FsStatScannerImpl}. Dopo aver letto il contenuto di una directory tramite l'API non bloccante \texttt{fs.readdir()} (da \texttt{fs/promises}), il metodo separa i risultati in file e sottodirectory, quindi lancia \textit{simultaneamente} tutte le operazioni figlie tramite \texttt{Promise.all}:

\begin{lstlisting}[language=Java]
await Promise.all([
  ...files.map((file) => exploreFile(file.name)),
  ...directories.map((dir) => exploreDir(dir.name)),
]);
\end{lstlisting}

Questo produce un \textit{fan-out} parallelo: tutte le chiamate a \texttt{fs.stat()} sui file e tutte le esplorazioni ricorsive delle sottodirectory vengono avviate in parallelo, senza attendere che una termini prima di avviare la successiva. La ricorsione si propaga in profondità nell'albero mantenendo questo stesso pattern ad ogni livello.

\paragraph{Assenza di sincronizzazione per costruzione.}

Una proprietà fondamentale di questo approccio è che l'aggiornamento dello stato condiviso — il metodo \texttt{updateReport(fileSize)} su \texttt{FsStatReportImpl} — avviene \textbf{senza alcun meccanismo di sincronizzazione} (niente lock, niente mutex, niente operazioni atomiche). Questo è sicuro per costruzione grazie alla \textit{run-to-completion semantics} di JavaScript: l'event loop garantisce che ogni callback venga eseguita interamente prima che un'altra possa iniziare. Due invocazioni di \texttt{updateReport} non possono mai sovrapporsi temporalmente, rendendo strutturalmente impossibile qualsiasi race condition sullo stato del report.

\paragraph{Gestione degli errori e robustezza.}

L'implementazione distingue due categorie di errori di I/O. Gli errori di accesso (\texttt{EACCES}, \texttt{EPERM}) vengono silenziosamente ignorati tramite \texttt{.catch()}, permettendo alla scansione di proseguire sui nodi raggiungibili. Gli errori strutturali (\texttt{ENOENT}, \texttt{ENOTDIR}) vengono invece convertiti in eccezioni tipizzate e propagati al chiamante, causando il rigetto della \texttt{Promise} restituita da \texttt{getReport}. È inoltre presente una \textit{blacklist} di path di sistema (\texttt{/proc}, \texttt{/sys}, \texttt{/dev} e altri) che vengono esclusi preventivamente dalla scansione per evitare loop infiniti o comportamenti non deterministici su filesystem virtuali.
\subsection{Approccio Reattivo con RX}
La terza tecnologia utilizza la Programmazione Reattiva, nella sua declinazione \textbf{RxJava}, un paradigma orientato ai flussi di dati (\textit{data stream}) e alla loro trasformazione dichiarativa tramite operatori funzionali. A differenza dei Virtual Thread e dell'Event Loop, dove la concorrenza è governata esplicitamente dal programmatore (sottomissione di task, composizione di \texttt{Promise}), nel modello reattivo è la libreria stessa a occuparsi dello scheduling: il compito dello sviluppatore si riduce a descrivere \textit{cosa} deve accadere ai dati che attraversano la pipeline, non \textit{come} e \textit{su quale thread} ciò debba avvenire.

\paragraph{Adattamento al problema.}

L'attraversamento del file system viene modellato come un flusso di eventi: ogni file incontrato durante la visita ricorsiva dell'albero di directory viene emesso come elemento di un \texttt{Flowable<File>}. Si tratta di un workload che presenta due nature distinte, ciascuna gestita da un meccanismo RX differente:

\begin{itemize}
    \item la \textbf{produzione} degli eventi (l'attraversamento delle directory tramite \texttt{File.listFiles()}) è un'operazione I/O-bound, intrinsecamente sequenziale nella sua fase di scoperta dei nodi dell'albero;
    \item il \textbf{consumo} degli eventi (la classificazione di ciascun file nella fascia di dimensione corretta e l'aggiornamento del report) è invece un'operazione CPU-bound, priva di dipendenze tra un file e l'altro, e quindi parallelizzabile senza vincoli.
\end{itemize}

Questa distinzione ha guidato la scelta degli operatori: la generazione dello stream avviene tramite un \textit{Publisher} custom, mentre l'elaborazione a valle sfrutta l'operatore \texttt{parallel()} di RxJava per distribuire il carico di classificazione su più thread.

\paragraph{Backpressure e disaccoppiamento produttore-consumatore.}

Poiché la fase di scoperta dei file può produrre eventi più velocemente di quanto la pipeline a valle riesca a consumarli (specialmente su alberi di directory molto popolati), è necessario un meccanismo di \textit{backpressure} che regoli il flusso tra produttore e consumatore evitando un consumo di memoria incontrollato o eccezioni di overflow. RxJava affronta questo problema tramite il tipo \texttt{Flowable}, che a differenza di \texttt{Observable} implementa nativamente il protocollo \textit{Reactive Streams}.

\paragraph{Cancellazione cooperativa.}

Un ulteriore vantaggio del modello reattivo, rilevante per il requisito opzionale di interruzione della scansione, è che ogni stream RX è \textit{cancellabile}: disiscriversi da un \texttt{Flowable} (o disporre di una \texttt{Disposable}) propaga automaticamente un segnale di cancellazione fino alla sorgente. Il produttore può interrogare periodicamente questo stato per interrompere tempestivamente un lavoro non più necessario, senza dover implementare a mano alcun meccanismo di interrupt flag condiviso, come sarebbe invece necessario con i thread tradizionali.

\section{Architettura e Design}

\subsection{Design dell'implementazione Virtual Threads}

L'implementazione con Virtual Threads è articolata in due classi principali nel package \texttt{it.unibo.fsstat.lib}: \texttt{FSReport}, che modella e protegge lo stato condiviso della computazione, e \texttt{FSStatLib}, che ne orchestra l'esecuzione concorrente. La GUI (\texttt{FSStatGUI}, nel package \texttt{it.unibo.fsstat.gui}) interagisce esclusivamente con l'interfaccia pubblica di \texttt{FSStatLib}, rimanendo ignara del paradigma di concorrenza sottostante.

\paragraph{Il modello dati: \texttt{FSReport}.}

\texttt{FSReport} incapsula tre informazioni: il conteggio totale dei file (\texttt{totalFiles}), i parametri di classificazione (\texttt{maxFS} e \texttt{nb}), e un array \texttt{distribution} di dimensione \texttt{nb + 1}. Le prime \texttt{nb} celle corrispondono alle bande di dimensione nell'intervallo \texttt{[0, maxFS]}, mentre la cella di indice \texttt{nb} raccoglie i file che superano \texttt{maxFS}. A differenza di un semplice \textit{value object} immutabile, in questa implementazione \texttt{FSReport} è anche l'oggetto di stato \textit{condiviso} tra tutti i Virtual Thread della scansione, e incapsula quindi al proprio interno anche la sincronizzazione necessaria a proteggerlo, tramite un \texttt{ReentrantLock} privato.

La classificazione di un singolo file avviene nel metodo \texttt{addFile(long size)}, che aggiorna contatore e array sotto lock e calcola l'indice di banda tramite divisione intera, restituendo atomicamente il nuovo totale di file:

\begin{lstlisting}[language=Java]
public int addFile(long size) {
    lock.lock();
    try {
        this.totalFiles++;
        double step = (double) maxFS / nb;
        int bandIndex = (int) (size / step);
        if (bandIndex == nb) bandIndex = nb - 1; // Caso limite: size == maxFS
        this.distribution[bandIndex]++;
        return this.totalFiles;
    } finally {
        lock.unlock();
    }
}
\end{lstlisting}

Il valore di ritorno evita al chiamante di dover rileggere separatamente il contatore dopo l'incremento, eliminando una possibile race condition tra scrittura e lettura. Non esiste più un metodo \texttt{merge()}: la fusione dei contributi dei vari Virtual Thread non è necessaria, poiché tutti scrivono direttamente sullo stesso oggetto. L'accesso in sola lettura al report è invece mediato da \texttt{getSnapshot()}, che restituisce, sempre sotto lock, una copia indipendente e coerente dello stato corrente (costruita tramite un costruttore privato di copia), usata sia come valore di ritorno finale sia per gli aggiornamenti incrementali verso la GUI.

\paragraph{La libreria: \texttt{FSStatLib}.}

L'interfaccia pubblica espone due sovraccarichi:

\begin{lstlisting}[language=Java]
public CompletableFuture<FSReport> getFSReport(
        String directoryPath, long maxFS, int nb)

public CompletableFuture<FSReport> getFSReport(
        String directoryPath, long maxFS, int nb,
        Consumer<FSReport> onUpdate, TaskController controller)
\end{lstlisting}

Il primo, richiesto dal requisito base della consegna, delega semplicemente al secondo passando \texttt{onUpdate = null} e un \texttt{TaskController} locale, non condiviso col chiamante e quindi mai cancellabile dall'esterno. Il secondo sovraccarico è invece quello che supporta il requisito opzionale di interruzione e monitoraggio incrementale, tramite un \texttt{Consumer<FSReport>} per la notifica dello stato parziale e un \texttt{TaskController} — un oggetto con un flag \texttt{volatile} \texttt{cancelled}, interrogabile con \texttt{isCancelled()} e impostabile con \texttt{cancel()} — condivisibile con il chiamante (nella GUI, ad esempio, per implementare il pulsante ``Stop''). La restituzione di una \texttt{CompletableFuture} disaccoppia comunque il chiamante dalla concorrenza interna: si possono concatenare callback (\texttt{thenAccept}, \texttt{exceptionally}) senza dover conoscere né i Virtual Thread né l'executor sottostante.

Internamente, la computazione viene incapsulata in una \texttt{CompletableFuture.supplyAsync()}. Prima di sottomettere il primo task viene istanziato l'unico \texttt{FSReport} \textit{condiviso} (\texttt{sharedReport}), che verrà passato per riferimento a ogni Virtual Thread della scansione. All'interno del contesto asincrono viene inoltre creato un \texttt{ExecutorService} dedicato ai Virtual Threads tramite \texttt{Executors.newVirtualThreadPerTaskExecutor()}:

\begin{lstlisting}[language=Java]
FSReport sharedReport = new FSReport(maxFS, nb);

return CompletableFuture.supplyAsync(() -> {
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        Path rootPath = Paths.get(directoryPath);
        processDirectory(rootPath, executor, sharedReport, onUpdate, controller).get();
        return sharedReport.getSnapshot();
    } catch (Exception e) {
        throw new CompletionException(e);
    }
});
\end{lstlisting}

Il blocco \texttt{try-with-resources} ha una funzione di lifecycle management precisa: alla sua uscita, \texttt{ExecutorService.close()} invoca \texttt{shutdown()} e \texttt{awaitTermination()}, assicurando che tutti i Virtual Thread lanciati ricorsivamente abbiano completato (o siano stati cancellati) la propria esecuzione prima che il risultato — una \textit{snapshot} immutabile del report condiviso — venga restituito alla \texttt{CompletableFuture}.

\paragraph{Il flusso ricorsivo: \texttt{processDirectory}.}

\texttt{processDirectory} è il cuore dell'algoritmo. Ogni sua invocazione sottomette all'executor un nuovo task — e quindi un nuovo Virtual Thread — incaricato di elaborare una singola directory, e restituisce un \texttt{Future<Void>} (non più \texttt{Future<FSReport>}: non c'è più nulla da restituire e fondere, dato che il risultato viene scritto direttamente sul report condiviso). Il flusso interno al task segue tre fasi:

\begin{enumerate}
    \item \textbf{Controllo di cancellazione e scansione}: all'ingresso del task viene verificato \texttt{controller.isCancelled()}; in caso positivo il task termina immediatamente. Si itera quindi sul contenuto della directory tramite \texttt{Files.newDirectoryStream()}, verificando la cancellazione anche a ogni iterazione. Per ogni file regolare, \texttt{Files.size()} legge la dimensione dal disco (operazione I/O bloccante) e la registra sul report condiviso tramite \texttt{sharedReport.addFile(...)}; se è stato fornito un \texttt{onUpdate} e il nuovo totale è multiplo di \texttt{NOTIFY\_EVERY\_N\_FILES}, viene notificata una snapshot del report parziale. Per ogni sottodirectory, si invoca ricorsivamente \texttt{processDirectory}, raccogliendo il \texttt{Future<Void>} restituito in una lista (\texttt{subTasks}).

    \item \textbf{Join e propagazione della cancellazione}: terminata la scansione, il Virtual Thread itera su \texttt{subTasks}. Se la cancellazione è stata richiesta nel frattempo, i task figli non ancora completati vengono cancellati con \texttt{task.cancel(true)}; altrimenti si chiama \texttt{task.get()}, che sospende il Virtual Thread — effettuando l'\textit{unmount} dal carrier thread — fino al completamento del figlio. \texttt{CancellationException} e \texttt{InterruptedException} vengono ignorate silenziosamente (interruzione volontaria), mentre eventuali \texttt{ExecutionException} vengono loggate su \texttt{stderr} senza interrompere la join delle altre sottodirectory.

    \item \textbf{Terminazione}: il task completa il proprio \texttt{Future<Void>} restituendo \texttt{null}, segnalando al padre di aver terminato la propria porzione di albero, senza alcun valore da propagare.
\end{enumerate}

La struttura risultante è comunque un albero di Virtual Thread isomorfo all'albero delle directory: ogni nodo dell'albero FS corrisponde a un task concorrente, ma a differenza della fase di riduzione di un classico Map-Reduce, ciò che si propaga bottom-up non è più un valore aggregato bensì il solo segnale di completamento (o di cancellazione).

\paragraph{Sincronizzazione e Thread Pinning.}

Tutti i Virtual Thread scrivono concorrentemente sullo stesso \texttt{sharedReport}: \texttt{addFile()} è quindi una sezione critica, protetta da un \texttt{ReentrantLock} interno a \texttt{FSReport} anziché da un blocco \texttt{synchronized}. La scelta non è stilistica: se un Virtual Thread si blocca all'interno di un monitor \texttt{synchronized}, non può effettuare l'unmount dal proprio carrier thread (\textit{Thread Pinning}), degradando lo scheduling quando molti Virtual Thread contendono la stessa risorsa. Il \texttt{ReentrantLock}, appartenendo alle API \texttt{java.util.concurrent} e non al meccanismo dei monitor a livello di bytecode, consente invece l'unmount anche mentre un Virtual Thread è in attesa del lock, preservando il vantaggio del modello \textit{Thread-per-task} anche in presenza di stato condiviso.

\paragraph{Gestione degli errori.}

Gli errori di accesso al file system (directory protette, symlink non risolvibili) vengono catturati localmente da un blocco \texttt{catch (IOException e)} all'interno di ciascun task: la directory inaccessibile viene saltata con un messaggio su \texttt{stderr}, mentre la computazione prosegue sui nodi raggiungibili. Eventuali eccezioni non gestite che sfuggono al task radice vengono incapsulate in una \texttt{CompletionException} e propagate al chiamante tramite la \texttt{CompletableFuture}, che entra nello stato \textit{exceptionally completed} e può essere intercettata con \texttt{.exceptionally()}.

\paragraph{Integrazione con la GUI: \texttt{FSStatGUI}.}

\texttt{FSStatGUI} è una GUI Swing minimale che espone un campo di testo per il percorso da analizzare, due pulsanti (\texttt{Start}/\texttt{Stop}) e un'area di testo per la visualizzazione del report. Alla pressione di \texttt{Start} viene creato un nuovo \texttt{TaskController} e invocato \texttt{getFSReport()}, passando come \texttt{onUpdate} una lambda che aggiorna l'area di testo tramite \texttt{SwingUtilities.invokeLater(...)} — necessario perché le notifiche arrivano da un Virtual Thread e Swing richiede che ogni modifica alla UI avvenga sull'\textit{Event Dispatch Thread}. Alla \texttt{CompletableFuture} restituita vengono concatenati un \texttt{thenAccept} (che mostra il report finale, distinguendo lo stato ``COMPLETATO'' da ``INTERROTTO dall'utente'' in base a \texttt{controller.isCancelled()}) e un \texttt{exceptionally} per la gestione degli errori. Alla pressione di \texttt{Stop}, \texttt{stopAnalysis()} si limita a invocare \texttt{currentTaskController.cancel()}, innescando la cancellazione cooperativa descritta in precedenza.

\subsection{Design dell'implementazione Event Loop}

L'implementazione con Event Loop è sviluppata in \textbf{TypeScript} sul runtime \textbf{Node.js}, ed è organizzata in moduli con responsabilità ben separate. A differenza della versione Java con Virtual Threads, l'intera concorrenza è ottenuta senza istanziare alcun thread esplicitamente: il parallelismo emerge dalla composizione di \texttt{Promise} gestite dall'event loop di Node.js e dal thread pool di \textit{libuv}.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{./immagini/typescript_architecture.png}
    \caption{Diagramma UML delle classi dell'implementazione con Event Loop (TypeScript).}
    \label{fig:uml-ts}
\end{figure}

\paragraph{Struttura dei moduli.}

Il codebase è suddiviso in moduli distinti, ciascuno con una responsabilità unica:

\begin{itemize}
    \item \texttt{report.ts} — modella il report statistico e la sua logica di aggiornamento;
    \item \texttt{scanner.ts} — implementa la logica di traversal asincrono del file system;
    \item \texttt{path.ts} — fornisce un tipo validato per i percorsi del file system;
    \item \texttt{sizes.ts} — utility per la conversione delle unità di dimensione dei file;
    \item \texttt{benchmark.ts} — utility per la misurazione dei tempi di esecuzione;
    \item \texttt{index.ts} — façade pubblica della libreria verso i consumer esterni.
\end{itemize}

\paragraph{Pattern di incapsulamento: factory function e interfaccia pubblica.}

Sia \texttt{FsStatReport} che \texttt{FsStatScanner} adottano un pattern idiomatico TypeScript per l'information hiding: la classe concreta (\texttt{FsStatReportImpl}, \texttt{FsStatScannerImpl}) è dichiarata \texttt{class} privata al modulo e non viene mai esportata. L'unico punto di accesso è la \textit{factory function} omonima, che restituisce l'interfaccia pubblica:

\begin{lstlisting}[language=Java]
export function FsStatScanner(): FsStatScanner {
  return new FsStatScannerImpl();
}
\end{lstlisting}

Il consumer non conosce mai la classe concreta né può accedere ai suoi membri privati: interagisce esclusivamente tramite l'interfaccia, che espone solo i metodi necessari (\texttt{getReport}, \texttt{updateReport}, \texttt{dto}). Questo garantisce un disaccoppiamento totale tra interfaccia e implementazione.

\paragraph{Il Branded Type \texttt{Path}.}

Il modulo \texttt{path.ts} definisce un \textit{Branded Type} per i percorsi del file system:

\begin{lstlisting}[language=Java]
export type Path = string & { readonly __brand: unique symbol };
\end{lstlisting}

Si tratta di un \textit{phantom type}: a runtime \texttt{Path} è semplicemente una stringa, ma a compile-time il type system di TypeScript impone che solo path prodotti da \texttt{createPath()} o \texttt{concatPaths()} — che normalizzano e validano l'input — possano essere passati alle funzioni interne dello scanner. Qualsiasi stringa grezza produce un errore di tipo a compile-time, eliminando un'intera categoria di bug senza alcun overhead a runtime.

\paragraph{Separazione del modello interno dall'API esterna: il metodo \texttt{dto()}.}

\texttt{FsStatReportImpl} mantiene internamente uno stato mutabile (\texttt{\_numOfFiles}, \texttt{\_sizeBands}), aggiornato ad ogni chiamata di \texttt{updateReport()}. Tuttavia, il consumer esterno non riceve mai accesso diretto a questo stato: il metodo \texttt{dto()} produce uno snapshot immutabile nel formato \texttt{FsStatReportDTO}, definito come tipo separato nel package dei tipi condivisi:

\begin{lstlisting}[language=Java]
dto(): FsStatReportDTO {
  return {
    numOfFiles: this.numOfFiles,
    sizeBands: [...this.sizeBands],  // copia difensiva
  };
}
\end{lstlisting}

La copia difensiva dell'array (\texttt{[...this.sizeBands]}) garantisce che il DTO sia uno snapshot indipendente: eventuali aggiornamenti successivi al report non alterano il risultato già consegnato al consumer.

\paragraph{Il flusso di traversal: \texttt{FsStatScannerImpl}.}

Il metodo pubblico \texttt{getReport()} istanzia un \texttt{FsStatReport} vuoto e avvia la traversal ricorsiva tramite \texttt{traverseDirectory()}, restituendo la \texttt{Promise} che si risolve al termine dell'intera scansione.

Il metodo \texttt{traverseDirectory()} costituisce il nucleo del design asincrono. Il suo flusso segue tre fasi:

\begin{enumerate}
    \item \textbf{Guard sulla blacklist}: prima di qualsiasi operazione I/O, il path viene verificato contro un \texttt{Set} di percorsi di sistema esclusi (\texttt{/proc}, \texttt{/sys}, \texttt{/dev}, \texttt{/run} e altri). Se il path è nella blacklist, la funzione ritorna immediatamente senza effettuare alcuna lettura, prevenendo loop infiniti o comportamenti non deterministici su filesystem virtuali.

    \item \textbf{Lettura della directory}: \texttt{fs.readdir()} con l'opzione \texttt{withFileTypes: true} restituisce direttamente le informazioni sul tipo di ciascuna voce (file o directory), evitando una chiamata aggiuntiva a \texttt{fs.stat()} per discriminarle. In caso di errore di accesso (\texttt{EACCES}/\texttt{EPERM}), il \texttt{.catch()} restituisce un array vuoto, permettendo alla scansione di proseguire sui nodi accessibili.

    \item \textbf{Fan-out parallelo con \texttt{Promise.all}}: file e sottodirectory vengono processati simultaneamente in un'unica barriera di sincronizzazione:
\begin{lstlisting}[language=Java]
await Promise.all([
  ...files.map((file) => exploreFile(file.name)),
  ...directories.map((dir) => exploreDir(dir.name)),
]);
\end{lstlisting}
    Tutte le chiamate a \texttt{fs.stat()} sui file e tutte le esplorazioni ricorsive delle sottodirectory vengono avviate in parallelo. L'event loop gestisce il completamento di ciascuna operazione in modo indipendente: non appena \texttt{fs.stat()} completa per un file, la relativa callback aggiorna il report senza attendere gli altri. \texttt{Promise.all} funge da barriera: \texttt{traverseDirectory} si risolve solo quando \textit{tutte} le operazioni figlie sono terminate.
\end{enumerate}

\paragraph{Gestione degli errori a due livelli.}

L'implementazione distingue esplicitamente due categorie di errori tramite il metodo \texttt{ignoreAccessError()}:

\begin{itemize}
    \item \textbf{Errori di permesso} (\texttt{EACCES}, \texttt{EPERM}): vengono silenziosamente ignorati. La scansione prosegue sui path accessibili, poiché è normale che alcune directory di sistema siano protette.
    \item \textbf{Errori strutturali} (\texttt{ENOENT}, \texttt{ENOTDIR}): vengono convertiti in eccezioni tipizzate tramite \texttt{parseScanningError()} e propagati al consumer come rigetto della \texttt{Promise} restituita da \texttt{getReport()}, segnalando una condizione anomala che richiede attenzione.
\end{itemize}

\paragraph{La façade pubblica: \texttt{index.ts}.}

Il modulo \texttt{index.ts} funge da unico punto di accesso alla libreria per i consumer esterni. Crea internamente un'unica istanza di \texttt{FsStatScanner} ed espone \texttt{getFSReport} come funzione standalone tramite \texttt{bind}, nascondendo completamente l'esistenza della classe:

\begin{lstlisting}[language=Java]
const scanner = FsStatScanner();
const getFSReport = scanner.getReport.bind(scanner);
\end{lstlisting}

Il consumer può importare \texttt{getFSReport} direttamente come funzione, senza mai istanziare né conoscere \texttt{FsStatScanner}. Questa scelta rispecchia lo stile funzionale prevalente nell'ecosistema Node.js, dove si preferisce esporre funzioni piuttosto che oggetti con stato esplicito.

\paragraph{CLI e misurazione delle prestazioni.}

Il modulo \texttt{main.ts} implementa la CLI: legge il path da \texttt{process.argv[2]} con fallback alla directory corrente (\texttt{process.cwd()}), configura i parametri (\texttt{maxSize = 100 MB}, \texttt{nb = 5}) tramite l'utility \texttt{FileSize.megabyte()}, e misura il tempo di esecuzione con \texttt{benchmark()}. Quest'ultima funzione, basata su \texttt{process.hrtime.bigint()} per precisione al nanosecondo, restituisce sia il risultato che la durata in millisecondi, che vengono poi stampati in formato JSON indentato tramite \texttt{JSON.stringify(report, null, 2)}.

\subsection{Design dell'implementazione RX}

L'implementazione reattiva è articolata, in analogia con la versione a Virtual Thread, in due classi principali del package \texttt{lib}: \texttt{Report}, che modella il risultato della computazione, e \texttt{FSStatLib}, che costruisce ed esegue la pipeline reattiva. La classe \texttt{Main} funge da consumer minimale, limitandosi a sottoscriversi al risultato prodotto dalla libreria.

\begin{figure}[h]
    \centering
    \includegraphics[width=1\textwidth]{./immagini/UML_Rx.png}
    \caption{Diagramma UML delle classi dell'implementazione con java RX.}
    \label{fig:uml-rx}
\end{figure}

\paragraph{Il modello dati: \texttt{Report}.}

\texttt{Report} è un oggetto mutabile che incapsula il conteggio totale dei file (\texttt{totalFiles}) e un array \texttt{sizeDistribution} di dimensione \texttt{nb + 1}, dove le prime \texttt{nb} celle corrispondono alle bande regolari nell'intervallo \texttt{[0, MaxFS]} e l'ultima cella raccoglie i file che superano \texttt{MaxFS}. Il metodo statico \texttt{calculateBandIndex(fileSize, maxFS, nb)} calcola l'indice di banda tramite divisione intera sull'ampiezza di banda \texttt{maxFS / nb}, gestendo separatamente i due casi limite: dimensione superiore a \texttt{MaxFS} (indice \texttt{nb}) e dimensione esattamente pari a \texttt{MaxFS} (ultima banda regolare, indice \texttt{nb - 1}), per evitare un accesso fuori dai limiti dell'array che si verificherebbe con un semplice arrotondamento.

Come nelle altre due implementazioni, il metodo \texttt{merge(Report other)} è l'operazione cardine della strategia Map-Reduce: somma componente per componente le due distribuzioni e accumula i totali. Trattandosi di una somma, l'operazione è associativa e commutativa, il che la rende sicura da applicare in qualsiasi ordine durante le fasi di riduzione della pipeline.

\paragraph{Generazione dello stream: \texttt{exploreDirectory}.}

Il punto di partenza della pipeline è il metodo privato \texttt{exploreDirectory(File dir)}, che costruisce un \texttt{Flowable<File>} tramite \texttt{Flowable.create()}:

\begin{lstlisting}[language=Java]
private static Flowable<File> exploreDirectory(File dir) {
    return Flowable.create(emitter -> {
        traverse(dir, emitter);
        emitter.onComplete();
    }, BackpressureStrategy.BUFFER);
}
\end{lstlisting}

La visita ricorsiva vera e propria è delegata al metodo di supporto \texttt{traverse()}, che scandisce l'albero di directory tramite \texttt{File.listFiles()}: per ogni sottodirectory richiama se stesso ricorsivamente, mentre per ogni file regolare invoca \texttt{emitter.onNext(file)}, immettendo l'elemento nello stream. A ogni iterazione viene verificato \texttt{emitter.isCancelled()}: se il consumer si è disiscritto (ad esempio tramite \texttt{dispose()} su una GUI che richiede l'interruzione), la visita si interrompe non appena possibile, evitando di proseguire un lavoro di cui nessuno è più interessato al risultato.

La strategia \texttt{BackpressureStrategy.BUFFER} è stata scelta perché la fase di scoperta dei file (l'unica parte della pipeline eseguita in modo strettamente sequenziale, dato che \texttt{traverse()} non è parallelizzato) può produrre elementi più velocemente di quanto gli stadi a valle riescano a consumarli su alberi di directory molto popolati; il buffer disaccoppia produttore e consumatore accodando gli eventi in eccesso, a costo di un potenziale utilizzo di memoria proporzionale al numero di file non ancora elaborati.

\paragraph{Parallelizzazione della classificazione: \texttt{ParallelFlowable}.}

Una volta ottenuto lo stream sequenziale di \texttt{File}, l'operatore \texttt{parallel()} lo converte in un \texttt{ParallelFlowable}, suddividendo virtualmente il flusso in un numero di \textit{rail} pari, di default, al numero di core disponibili. L'operatore \texttt{runOn(Schedulers.io())} assegna concretamente ciascun rail a un thread dello scheduler I/O di RxJava (un pool elastico, pensato per un elevato numero di operazioni brevi e potenzialmente bloccanti), che è dove viene effettivamente eseguito il lavoro di classificazione:

\begin{lstlisting}[language=Java]
return exploreDirectory(rootDir)
    .parallel()
    .runOn(Schedulers.io())
    .map(file -> {
        Report partialReport = new Report(nb);
        int bandIndex = Report.calculateBandIndex(file.length(), maxFS, nb);
        partialReport.recordFile(bandIndex);
        return partialReport;
    })
    .collect(() -> new Report(nb),
             (railReport, partialReport) -> railReport.merge(partialReport))
    .sequential()
    .collect(() -> new Report(nb),
             (mainReport, railReport) -> mainReport.merge(railReport));
\end{lstlisting}

Per ciascun file, l'operatore \texttt{map} produce un \texttt{Report} "puntuale", contenente il conteggio di un solo file già classificato nella banda corretta tramite \texttt{Report.calculateBandIndex()} e \texttt{recordFile()}. Questa scelta rende l'operazione di mapping pura e priva di effetti collaterali: ogni thread lavora esclusivamente su oggetti a sé locali, senza mai leggere o scrivere uno stato condiviso con gli altri rail.

\paragraph{Riduzione a due livelli.}

L'aggregazione dei report avviene in due fasi distinte, rispecchiando la struttura a "rail" del \texttt{ParallelFlowable}:

\begin{enumerate}
    \item Il primo \texttt{collect()}, eseguito ancora in contesto parallelo, fonde i \texttt{Report} puntuali prodotti da ciascun rail in un unico \texttt{Report} \textit{di rail}, tramite un accumulatore locale (\texttt{() -> new Report(nb)}) e la funzione di fusione \texttt{railReport.merge(partialReport)}. Poiché ogni rail possiede un proprio accumulatore privato, questa riduzione non richiede alcuna sincronizzazione: nessun altro thread accede contemporaneamente allo stesso \texttt{Report}.
    \item L'operatore \texttt{sequential()} ricongiunge i rail paralleli in un unico \texttt{Flowable} standard, emettendo in sequenza i (al più \textit{n} core) report parziali di rail.
    \item Il secondo \texttt{collect()} esegue la riduzione finale, fondendo sequenzialmente tutti i report di rail in un unico \texttt{Report} conclusivo, restituito come \texttt{Single<Report>}.
\end{enumerate}

Questa struttura a doppia riduzione è concettualmente identica al pattern Map-Reduce adottato dalle altre due versioni (fusione bottom-up di risultati locali), ma qui la "gerarchia" non rispecchia l'albero delle directory bensì la suddivisione in rail del \texttt{ParallelFlowable}: è la libreria RxJava, e non il programmatore, a decidere in quale rail e su quale thread ciascun elemento dello stream venga elaborato.

\paragraph{Assenza di sincronizzazione esplicita.}

Come nelle altre due implementazioni, in nessun punto della pipeline compaiono \texttt{synchronized}, \texttt{Lock} o variabili atomiche. La sicurezza rispetto alle race condition non deriva qui dall'assenza di stato condiviso (come nei Virtual Thread) né dalla \textit{run-to-completion semantics} di un singolo thread (come nell'Event Loop), bensì da una garanzia strutturale di RxJava: gli operatori \texttt{collect()} invocano il proprio accumulatore in modo strettamente sequenziale all'interno di ciascun rail, e ogni rail possiede un accumulatore proprio, non condiviso con gli altri. La libreria si fa quindi carico di serializzare gli accessi allo stato mutabile del report, sollevando lo sviluppatore da qualsiasi responsabilità di sincronizzazione manuale.

\paragraph{Integrazione con la CLI: \texttt{Main} e ponte verso il modello bloccante.}

Il metodo pubblico \texttt{getFSReport()} restituisce un \texttt{Single<Report>}, il tipo RX più adatto a rappresentare una computazione asincrona che produce esattamente un risultato (o un errore), analogo concettualmente alla \texttt{CompletableFuture} della versione a Virtual Thread. In \texttt{Main}, la sottoscrizione avviene tramite \texttt{subscribe()} con due callback distinte, per il caso di successo e per il caso di errore:

\begin{lstlisting}[language=Java]
reportSingle.subscribe(
    report -> { System.out.println(report); latch.countDown(); },
    error  -> { System.err.println(error.getMessage()); latch.countDown(); }
);
\end{lstlisting}

Poiché la sottoscrizione è per sua natura non bloccante, il thread principale terminerebbe immediatamente senza attendere il risultato: per questo motivo \texttt{Main} introduce un \texttt{CountDownLatch(1)}, decrementato da entrambe le callback, e ne attende il rilascio con \texttt{latch.await()}. Questo meccanismo funge da ponte esplicito tra il mondo asincrono della pipeline reattiva e il modello di esecuzione sincrono di una CLI testuale, con un ruolo analogo a quello svolto da \texttt{.get()}/\texttt{.join()} nella versione a Virtual Thread.

\paragraph{Gestione degli errori.}

Se il percorso fornito non esiste o non è una directory, \texttt{getFSReport()} restituisce immediatamente un \texttt{Single.error()}, senza avviare alcuna elaborazione. Qualsiasi eccezione sollevata all'interno della pipeline (ad esempio durante l'accesso al file system) viene automaticamente incanalata da RxJava verso il canale di errore dello stream, raggiungendo la callback \texttt{onError} passata a \texttt{subscribe()} senza necessità di propagazione manuale tramite blocchi \texttt{try-catch} espliciti nel codice applicativo.
